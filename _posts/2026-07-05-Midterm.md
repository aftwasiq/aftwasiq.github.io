## First Deliverable (two-way UART transport + Scrutiny integration)

This was my primary focus throughout the first half of GSoC. Making sure Scrutiny boots up with RTEMS through not only physical hardware, but emulation was my primary goal, on both little endian & big endian architectures. The focus on the emulator aspect is due to the easiness of testing the integration for maintainers. 

So far, this integration effort has been tested on STM32F401RE physical hardware & LEON3 QEMU. 

The first week introduced one roadblock in running Scrutiny with RTEMS via SIS. Before I chose QEMU, my initial idea was to test it through SIS (sparc instruction simulator). Unfortunately, this is the only target (so far) which this integration does not work on. My first week was spent constantly debugging through the emulated firmwares handshaking with the Scrutiny server whilst using socat as a middleman. Thankfully, it is not required for this integration to work on all targets due to the nature of it being an optional experience. However, I will still raise an issue after GSoC to look into this, more info on my blog post from the first week.

The rest of the process that went on for the following 2 weeks involved a lot of research. Mainly research into the best timestamp methodology to use from RTEMS and how to initialize RTEMS tasks in a seamless manner. I took a lot of inspiration from existing testsuites, aswell as discussion with my mentors. For getting timestamps for Scrutiny, I settled on using CLOCK_MONOTONIC with clock_gettime(). For setting up RTEMS tasks to hook onto Scrutiny datalogging, I followed through the implementation of RTEMS tasks from the testsuite ticker.c.

The final bit of this deliverable was to ensure variable from my RTEMS demo file are actually available to instrument to Scrutiny. This involved either initializing Runtime-Published variables (which the user does themselves) or postbuild generation of an SFD, which is a Scrutiny Firmware Description file. The SFD contains important information like the firmware id, variable map, and aliases in order to tell the Scrutiny GUI what to instrument. I integrated this postbuild integration to my demo file and was able to successfully instrument variables from my demo file.
